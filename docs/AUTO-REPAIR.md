# 无人值守故障修复

正常签到仍由本地程序执行。整轮结束后，若当天启用的任务仍有可排查的失败，助手会自动向绑定的 Codex 聊天投递修复请求。无需用户看到 5/6 后再发消息，也不逐次要求确认代码修复或补跑。

## 触发和补跑

引擎在清理窗口和释放自身锁后发出失败事件。短时投递进程等待工作台记录终态，再读取本地日志、子任务结果和截图位置；不会自行操作微信，也不创建第二个签到计划。成功、模拟、旧日期、活动不存在、过期口令及明确人工验证不会直接触发改代码。网络故障优先沿用工作台已有重试。

同一源执行只有一份故障报告和一个 job。Codex 必须先认领；重复消息不能重复修复。用户暂停全部计划、停用任务、切换账号或任务配置后，旧请求失效。每天最多两个修复请求，每个请求最多一次修复部署和一次正式补跑。投递失败会持久保存并退避；回执超时不自动启动第二个代码修改者。

修复者先复现问题，用模拟数据写回归并运行必要测试，保留旧模块，再在业务空闲时部署。补跑通过工作台原队列和业务锁，已完成项跳过。只有源数据库当天真实 `desktop` 完成记录和全部启用子任务同时通过核验，`finish` 才允许记录修复完成。无法修复仍保留未完成状态。

## 原生巡检兜底

开发电脑已绑定当前聊天的 Codex 自动化「永劫签到失败自动修复」。香港时间每天 **05:15、07:15、09:15、11:15、13:15、15:15、17:15** 检查一次。它使用 `prepare`，不向自己重复投递；没有失败或已有修复者时安静结束。巡检会消耗少量 Codex 额度。电脑和桌面应用需要保持运行，自动修代码需要可用的 Codex 登录、网络和额度。真实微信/游戏操作还需要可用的 Windows 桌面；锁屏不会被绕过。

事件投递通常比巡检更早发现失败。额度不足时登记恢复时间，后续巡检继续；不会购买额度或自动使用重置次数。扫码、验证码、账号限制或活动终止不能靠改代码消除，遇到真实人工阻塞会保存原因。

## 本地状态与操作

设置在 `%LOCALAPPDATA%\NarakaCheckinAssistant\repair\config.json`，包含 `enabled`、绑定 `thread_id`、`max_daily_jobs` 和原生自动化 ID。配置默认不存在即停用，不随公共源码分发个人聊天 ID。其他电脑需要在自己的目标 Codex 聊天中请求启用、绑定自己的聊天 UUID，并创建同名原生巡检；复制源码不会自动创建这些绑定。日志和证据保存在同目录的 `jobs.sqlite3`、`reports/`、`watch.log` 与 `last-check.json`，不上传个人截图或凭据。

在项目目录使用：

```powershell
& 'D:\NarakaCheckinAssistant\.venv\Scripts\python.exe' -m assistant.repair_bridge status
& 'D:\NarakaCheckinAssistant\.venv\Scripts\python.exe' -m assistant.repair_bridge prepare
```

修复流程命令为 `claim --job ID`、`retry --job ID`、`finish --job ID`；暂时等待使用 `defer --job ID --until '带时区的ISO时间'`，确实不可处理使用 `block --job ID --reason '原因'`。`retry` 的请求响应丢失时只记录未知状态，先核对工作台，禁止盲目重复提交。

要停用，只需将修复配置的 `enabled` 改为 `false`，并在 Codex 中暂停上述同名自动化；这不改变05:00签到计划。软件回退先执行上述停用，再恢复引擎备份并移除本次新增模块，不还原签到数据库或账号配置。

## 验收范围

测试覆盖执行中5/6不触发、结束后5/6投递、6/6不请求修复、并发去重、人工暂停、过期/人工验证、投递退避、额度等待、真实结果核验、补跑请求去重，以及引擎收尾事件顺序。模拟通过不代表真实签到成功。
